# Configurator: validation + recommendation-rules worksheet Implementation Plan

> Executed task-by-task. Each task is a self-contained unit with checkbox steps (2–5 min each), explicit verification, and a final commit. Check off `- [ ]` items as you complete them. Do not batch tasks; finish and commit one before starting the next.

**Goal:** Validate the already-built configurator (§9), close the one real gap (the emailed lead must flag *every* recommendation a user engaged with — not only rewrite-type ones), formalise `configurator-rules.json` as a maintained worksheet with a documented edit/regenerate workflow, and harden the rules-engine + email vitest coverage.

**Architecture:** The configurator is a client-side `useReducer` wizard (`src/app/configurator/Wizard.tsx` + `state.ts` + `step-graph.ts`) whose answers drive a small data-driven rules engine (`rules.ts` reading `src/data/configurator-rules.json`). Rule gates fire on step transitions, surfacing a `RecommendationHint` card ("Aplică recomandarea" / "Citește mai mult" + the *why*). On submit, the wizard POSTs answers + `acceptedRule` + `originalAnswers` to `src/app/api/configurator/submit/route.ts`, which renders `src/lib/email-templates/configurator-lead.ts` and sends via Postmark. This plan touches the engine, the accept/decline state, the email template, the rules data, and tests — it does **not** rebuild the wizard UI.

**Tech Stack:** Next.js 15.5 (App Router, Turbopack), React 19.1, TypeScript 5, Tailwind CSS 4, Framer Motion 12, Zod 4, lucide-react, Postmark, Vitest 4 (+ jsdom, @testing-library/react). Spec PDF is generated by a zero-dep Node script driving headless Chrome (`scripts/build-configurator-spec.mjs`).

**Files:**

**Interfaces:** none (documentation). References the `Rule` type in `src/app/configurator/rules.ts` and the script `scripts/build-configurator-spec.mjs`.

- [ ] Create `src/data/configurator-rules.README.md` with:
  ```markdown
  # configurator-rules.json — worksheet de întreținere

  Acest fișier este o **fișă de lucru vie**. Regulile se adaugă și se revizuiesc
  în timp, împreună cu Teo. Nu e o structură "terminată la lansare".

  ## Ce este o regulă
  Fiecare intrare e un obiect `Rule` (vezi `src/app/configurator/rules.ts`):

  ```ts
  type Rule = {
    id: string;                 // unic, kebab-case, stabil (apare în email)
    if: Partial<Answers> & { lengthBelow?: number; totalM2Below?: number };
    then: {
      suggest: string;          // eticheta internă a alternativei
      title?: string;           // titlul cardului
      message: string;          // mesajul scurt "in your face"
      detail?: string;          // textul lung din "Citește mai mult" (de ce-ul)
      rewriteAnswers?: Partial<Answers>; // dacă există, apare butonul "Aplică"
    };
  };
  ```

  ## Cum se evaluează (important pentru ordine)
  `evaluateRules` întoarce **prima** regulă din array care se potrivește și care
  nu a fost deja afișată. Așadar **ordinea contează**: pune regulile specifice
  înaintea celor generice (ex. `public-nesupervizat-fundatie` înainte de
  `fara-fundatie`).

  ## Condiții (`if`)
  - Orice cheie din `Answers` se compară prin egalitate strictă
    (`projectType`, `sport`, `useCase`, `users`, `context`, `baseLayer`, `timeline`).
  - `lengthBelow: N` → se potrivește dacă `length < N`.
  - `totalM2Below: N` → se potrivește dacă `totalM2 < N`.
  - Toate cheile dintr-un `if` trebuie să se potrivească (ȘI logic).

  ## Când apare recomandarea
  Regulile se evaluează la trecerea prin "gate"-uri (vezi `RULE_GATES` în
  `Wizard.tsx`): `context`, `users`, `interior-env`, `dimensions`, `base-layer`.
  O condiție care depinde de un răspuns dat **după** ultimul gate nu va declanșa
  niciodată — verifică `step-graph.ts` pentru ordinea reală a pașilor.

  ## Cum adaugi o regulă nouă
