## Contract Freeze (OVERRIDES all sub-plans)

The sub-plans were authored in parallel and disagree on three shared contracts. These are the canonical definitions. Where a sub-plan differs, **this section wins.**

### 1. Servicii category slugs — canonical (flat URLs)

URLs are **flat**: `/servicii/[category]`. The mega-menu groups them visually under Interior/Exterior headings, but the slug never includes the group. The 8 canonical slugs + Romanian labels:

| Group | Slug | Label |
|-------|------|-------|
| Exterior | `sport-outdoor` | Pardoseli sportive outdoor |
| Exterior | `locuri-joaca` | Pardoseli pentru locuri de joacă |
| Exterior | `pardoseli-piatra` | Pardoseli de piatră |
| Exterior | `alei-pietonale` | Alei pietonale |
| Interior | `sport-indoor` | Pardoseli sportive indoor |
| Interior | `mocheta` | Mochetă |
| Interior | `pvc-linoleum` | Covor PVC / Linoleum / Tapet PVC |
| Interior | `lvt` | LVT |

**Every** href to a service category — homepage hero slides, Despre "Direcțiile noastre" cards, Proiecte "Sistem" links, mega-menu — uses exactly these slugs. **Reject** homepage's nested `/servicii/exterior/...` scheme and the `systems.json` `multisport`/`piste-atletism` slugs for service URLs.

### 2. Proiecte filter categories + service→project mapping

Project portfolio categories (the `gallery.ts`/`projects.json` filter axis) are a **separate** taxonomy describing finished work. Canonical set (keep `locuri-joaca` as its own — do **not** merge into `educational`):

`piste-atletism` · `multisport` · `locuri-joaca` · `spatii-publice` · `interioare` · `constructii-cheie`

Service category → project filter (`relatedProjectCategory`, used by Servicii `RelatedProjectsLink`):

```ts
const SERVICE_TO_PROJECT: Record<ServiceSlug, ProjectCategory> = {
  'sport-outdoor':    'multisport',
  'locuri-joaca':     'locuri-joaca',
  'pardoseli-piatra': 'spatii-publice',
  'alei-pietonale':   'spatii-publice',
  'sport-indoor':     'multisport',
  'mocheta':          'interioare',
  'pvc-linoleum':     'interioare',
  'lvt':              'interioare',
}
```

Fix Servicii `services.test.ts` so its allowed-category assertion uses exactly this `ProjectCategory` set (it currently still asserts a stale set). Plan G's `gallery.ts` `ProjectCategory` union must equal the 6 above.

### 3. 3D component API — canonical (flooring-3d owns it)

Plan A (`flooring-3d`) owns the 3D types and exports. Canonical contract:

```ts
// src/components/home/FlooringSystem/index.ts (Plan A)
export type FlooringSystemId =
  | 'sport-outdoor' | 'sport-indoor' | 'locuri-joaca' | 'pardoseli-piatra' | 'gazon-sintetic'
export interface FlooringLayer { label: string; thicknessMm: number; texture: string }
export interface FlooringSystem { id: FlooringSystemId; title: string; layers: FlooringLayer[] }

// Full section (service page / standalone): the big interactive exploded view
export function FlooringSystemSection(props: { system: FlooringSystem; sectionId?: string }): JSX.Element
// Mega-menu mini model: small autoplay loop, keyed by id
export function FlooringMiniModel(props: { systemId: FlooringSystemId; autoRotate?: boolean; interactive?: boolean }): JSX.Element
export function getFlooringSystem(id: FlooringSystemId): FlooringSystem
```

**Corrections this forces on Plan A:** its `FlooringSystemId` values must be the 5 above (rename `spray-sportiv`→`sport-outdoor`, `loc-de-joaca`→`locuri-joaca`, `teren-sport-outdoor` dropped, `piatra-resin`→`pardoseli-piatra`), and it must **add a dedicated `sport-indoor` system** (the spec's mandatory indoor/outdoor split — F3 23:41). `gazon-sintetic` (cork) stays as a 5th system surfaced as a variant under `sport-outdoor`.

**Corrections this forces on Plan C (`servicii`):** `CategoryMega3D` consumes `FlooringMiniModel({ systemId })`, **not** the non-existent `FlooringModel({ modelId, variant })`. Service category → 3D system map (categories not listed have **no** 3D — they use `CategoryLayerPhoto` only, which is allowed):

